# dsh-text-manager · 文本管理器

DSH 对话的文本管理插件，**两个互相独立的模块**，各有各的总开关：

| 模块 | 做什么 | 默认 |
| --- | --- | --- |
| **① 翻译模块** | 把英文**思考链**和**思考之间的零散文字**自动翻译成中文 | 开 |
| **② 文字样式模块** | 自定义对话内各类文字的字体、字号、颜色、间距与边框（正文 / 旁白 / 引用 / 命令说明 / 思维翻译 …） | 关 |

两个开关互不影响：翻译关掉，样式模块照样能用（比如你只想让正文变大、旁白变淡）。

> 这是一个 **DSH 插件包**（host half + browser half），不是独立程序。装进某个 profile 后在设置面板里配置即可。


> **本插件已经拆成两支**：**dsh-text-translator**（本插件，只管翻译：思考链、思考之间的零散
> 文字、每个对话的独立开关）和 **dsh-text-styles**（只管对话内文字样式）。两者互相独立，可分别
> 安装、启用和更新。下面文档中关于「文字样式模块」的章节已归属 dsh-text-styles，保留在此仅供对照；
> 翻译相关的部分全部有效。

## 模块①：翻译

### 它做了什么

- **两类内容都会翻译**：思考链（thinking），以及**思考块之间那些零散的助手文字** —— 模型在工具调用之间说的一两句英文，例如「Now let me update the tests…」。两者走完全相同的机制：增量翻译、落盘、可逐条刷新、可分别开关。
- **加载时不会闪一下。** 页面打开时每一轮都已经存在，插件先认领、再判定；在判定回来之前**什么都不显示** —— 早先版本会先画一个占位块（还标着 `旁白翻译`），判定为「无需翻译」后又自己消失，看起来像每轮下面都闪一下。正在流式输出的行和你点过按钮的行例外，那里占位块就是反馈本身。（判定是纯本地的，不花钱。）
- **只翻译新产生的内容。** 页面打开后新流式输出的内容会自动翻译；**以前对话里的思考链和零散文字都不会自动翻译**，一分钱也不会花。每条内容旁边都有按钮，需要时点一下。
- 翻译块随内容流**增量**输出中文（按段落切分，一段一段翻）。
- **译文会落盘固定下来。** 一段文字翻译过一次就存进译文库，之后无论重开对话、刷新页面还是重启 Harness，都是**原样回放同一段中文**，不再调用模型；只有你手动点「刷新」才会重翻并覆盖。
- 翻译请求由 **本机 Host** 发出，直连你配置的 DeepSeek（或任意 OpenAI 兼容）接口 —— 不受浏览器 CORS 限制，**API Key 也不会进浏览器存储**。
- 设置页面（**设置 → 文本管理器**）里可以配置：开关、API Key（可点「显示明文」核对）、接口地址、**模型（可一键拉取接口的模型列表后挑选，也能手填）**、**翻译模型的思考模式（自动 / 开启 / 关闭）**、**是否自动展开思考链**、**是否翻译思考之间的零散文字**、**是否连历史一起翻译**、只翻译英文、分段上限、超时，并且内置 **翻译自检** 按钮。

### 每条内容上的按钮

| 按钮 | 什么时候显示 | 做什么 |
| --- | --- | --- |
| **翻译** | 这段还没翻译（历史内容默认就是这种） | 翻译它。已经存过的段落直接复用，只对没有的段落花钱 |
| **刷新** | 这段已经翻好了 | **重新翻译并覆盖**已保存的译文 —— 这是唯一会重翻的操作 |
| 复制 / 收起 | 有译文时 | 复制中文；折叠或展开译文块 |

还没翻译的内容只显示一行很淡的 `中文翻译 · 未翻译 · [翻译]`，鼠标移上去才变实。译文块贴在原文下面，原文始终保留。

### 三种译文怎么区分

思考块翻译和零散文字翻译**刻意做成不一样的样子**，一眼能分出来：

| | 竖条 | 底色 | 圆角 | 角标 | 悬浮提示 |
| --- | --- | --- | --- | --- | --- |
| **思考块**（在思考区域内） | 2px 实线，品牌色（浅色主题下接近黑、深色主题下接近白） | 卡片底色 | 圆角 | `中文翻译` | 思考链的中文翻译 |
| **零散文字**（在正文流里） | **3px 虚线，`label-tertiary` 灰** | **无** | **直角** | `旁白翻译` | 思考块之间零散文字的中文翻译 |
| **回答正文** | 2px 实线，品牌色 | 卡片底色 | 圆角 | `正文翻译` | 回答正文的中文翻译 |

竖条的宽度、线型、颜色三处都不同，加上角标文字和底色差异，三者不会看混。

**为什么回答下面也会有译文块？** DSH 让**回答正文**和**零散文字**走同一条渲染路径（都是 assistant-step 的 response 部分），DOM 里没有现成标记。插件用和 DSH 判定 `answerStep` 相同的规则来区分：**同一轮里最后一个 response 部分就是回答**（`tools/probe-session.mjs` 可以把任意会话的步骤结构打出来核对）。所以：

- 回答的译文角标是 `正文翻译`，零散文字的译文角标是 `旁白翻译` —— 早期版本一律写 `旁白翻译`，看起来就像「正文后面又冒出一段旁白」，1.6.2 修掉了。
- 中文正文通常**整块都不显示**（被「只翻译英文」跳过）。只有正文里含足够多的英文（例如结尾一堆文件链接）时才会出现译文块 —— 而现在这种「只有路径/链接/标识符」的片段会被直接跳过（见下面的设置说明），所以回答下面一般不会再凭空多出一块。

配色是**从安装产物里读出来的真值**，不是估的：`tools/make-preview.mjs` 会把插件样式表和 `@deepseek-ai/dsh-client-ui-theme` 里的主题变量一起抽出来，生成 `preview/prose-style.html`（浅色/深色并排），可以直接在浏览器里打开对照。

> 这个预览顺手拦下一个真问题：最初给零散文字选的竖条颜色是 `--dsw-alias-border-l2`，而它的真实值是 `#0000001a`（10% 黑）—— 浅色主题下几乎看不见。换成 `label-tertiary` 后才真正能用。**凭感觉挑主题变量不可靠，得看真值。**

**已经是中文的段落会让整块消失。** 被「只翻译英文」跳过的段落不产生任何显示；如果一条内容的所有段落都被跳过（最终回答通常是中文），那一块连按钮都不显示 —— 否则每个中文回答下面都会多出一行没用的提示。想强制翻就把「只翻译英文」关掉。

## 安装

已经通过官方插件管理器安装进 `desktop` profile：

```text
dsh-text-manager  →  file:E:/Data/Project/DeepSeekHarness/DSH-Homemade-Plugins/dsh-text-manager
```

它做了三件事：

1. 在 `%DSH_HOME%/profiles/<profile>/package.json` 里加入依赖 `dsh-text-manager`；
2. 把 `dsh-text-manager` 加进 `dsh.profile.bundles`；
3. 由 `cordis.patch.yml`（`dsh.bundle.patch` 指向它）插入 Loader 行 `text-manager`。

`node_modules/dsh-text-manager` 当前是指向本目录的 **junction**，所以直接改本目录的源码即可，不需要重新安装。

> ⚠️ **Host 半边的改动需要重启 DeepSeek Harness 才会生效。** 当前 profile 的 HMR 关闭了模块监听（`root: []`），Cordis 也不会重新 import 已缓存的模块；只有浏览器半边能热更新。**1.4.x 的成本改造、自动展开修复与款式区分都改了浏览器半边，必须重启一次**（或用 设置 → 插件 里的重启）。判断方法：设置页顶部状态行出现 `v1.6.3` 就说明 Host 半边已经是新的；设置页里能看到「翻译粒度」下拉，就说明浏览器半边也是新的。
>
> 只改 `lib/client.js` 的修复（比如「一趟扫描只读一次 DOM 索引」那次）不需要重启 Host：浏览器半边会热更新，没热更新就刷新页面（Ctrl+R）。确认方法是 `npm test`，以及实测 —— 在一条很长的会话里点轮次轨道最前面的一轮，窗口应当保持可响应。

### 卸载

```powershell
# 在设置 → 插件 里关闭/卸载，或：
# 删除 profile package.json 中的依赖与 bundles 条目，然后把 node_modules 里的 junction 删掉
```

## 模块②：文字样式

目标很直接：**让对话里不同性质的字看起来就是不同的**，而不是全都一个样子。这一模块只改样式，不碰内容。

开关在设置页最上面的「模块」区，和翻译模块并列、互相独立。

### 可以自定义的内容

| 分组 | 项目 | 作用对象 |
| --- | --- | --- |
| 主要内容 | **正文** | 最终回答的 markdown 正文 |
| | **旁白** | 步骤之间那些零散文字（例如「Now let me update the tests…」） |
| | **思维翻译** | 插件贴在思考块下面的中文译文块 |
| | **旁白翻译** | 插件贴在零散文字下面的中文译文块 |
| 强调与引用 | **着重** | 正文里的粗体/斜体 |
| | **引用** | `blockquote` |
| | **链接** | 正文里的 `a` |
| 结构 | **标题** | 正文里的 `h1`–`h6` |
| | **列表** | `ul`/`ol` |
| 代码与命令 | **行内代码** | 正文里的 `code` |
| | **代码块** | 正文里的 `pre` |
| | **命令说明** | 工具卡片里那行说明文字（`[data-caption]`） |
| | **工具输出** | 工具卡片的输出/差异/读取正文 |
| 其他 | **我的消息** | 你自己发的那条消息 |

每一项都自带 **3–6 个预设**，另有 **近二十个可微调的旋钮**：字体、字号、行高、字重、斜体、字距、文字色、不透明度、对齐、背景、圆角、下划线，以及**每一项都有**的 **左边距 / 右边距 / 上下内边距 / 上下外边距** 和 **边框开关**（无 / 左 / 右 / 上 / 下 / 四周 + 粗细·实虚线·颜色）。

左边距是分开的一项，因为竖线边框最需要它：正文的自带样式没有左右内边距，加竖线后文字会贴着线，把「左边距」调到 12–16px 就分开了（上面那份画廊的最后一栏就是这个组合）。

### 可视化

三层都是看得见的，不用靠想象：

- **每一项都能单独加边框**：边框开关对全部 14 项都可用 —— 无边框 / 左侧竖线 / 右侧 / 上边 / 下边 / 四周，粗细、实虚线、颜色都能选。选了一侧就只留那一侧（自带的那条也会一并去掉），选「无边框」就是把自带竖线摘掉。以前的「左侧竖线」语义保留着：只设粗细/线型/颜色而不动开关，仍然是左侧竖线，所以内置预设的行为没变。
- **预设标签自己就是样例**：每个预设按钮里渲染一段「示例文字 Aa」，用的是该预设**真实生成的那套 CSS**，所以「紧凑 / 宽松 / 大字 / 卡片 / 荧光笔」长什么样一眼可辨。
- **设置页里有一段完整示例**：用户消息 → 思维翻译 → 旁白 → 旁白翻译 → 回答正文（内含着重、链接、行内代码、引用、列表、代码块）→ 工具卡片（命令说明 + 输出）。它由**和真实对话完全相同的那份 CSS** 渲染，改任何一项立刻反映在它上面。
- **「在对话中立即生效」（默认开）**：开了就是真的即时生效 —— 改动直接写进正在显示的对话，不需要保存、不需要刷新。关掉后只影响设置页里的示例（保存后下次打开仍然生效）。
  - **未保存的改动不会被后台刷新冲掉**：设置文档会在每次切回窗口时重新拉取，而草稿在保存前一直优先（早期版本会被拉取结果覆盖，于是「改了一半切个窗口就变回默认样式」，1.6.3 修掉）。**离开设置页而不保存**等于放弃草稿，对话恢复成已保存的样子 —— 想留住就点保存。
  - **样式引擎重启后仍然有效**：停止再启动会真正复活（早期版本停止后再启动，正文/旁白这些依赖标记的样式会静默失效）。

实现上不碰任何 React 节点：所有样式都是一条 `<style>` 里的规则，挂在 DSH 自己的 DOM 契约上（`data-chat-flow-kind` / `data-chat-group-part` / `data-chat-call-id` / `data-caption` / `class*="markdown"`）。所以它**不会和聊天自己的渲染打架**，关掉模块也只是把那条样式表清空。

- **不想重启也能先看**：`preview/text-style.html` 是用模块自己的 CSS 生成器做出来的预设画廊（原样 / 紧凑 / 重点突出 / 等宽 / 淡雅卡片 / 自选边框 六种组合并排），重新生成用 `node tools/make-style-preview.mjs <解包出来的 dsh-client-ui-theme 目录>`。

### 正文和旁白是怎么分开的

这两者 DSH 走的是**同一个渲染路径**（都是 assistant-step 的 `data-chat-group-part="response"` 流程项），DOM 里没有现成的标记。DSH 自己用的是「这一轮最后一个 assistant step 就是回答」（`answerStep`）。同样的信息从 DOM 也读得出来：

> **同一轮里最后一个 response 项就是正文，它前面的都是旁白。**

模块用一条自己的观察循环给这些流程项打上 `data-dsh-tm-part="answer|narration"`（只在这个模块开启时打；关掉时会把标记清掉）。代价是：如果模型先输出一段话、之后这一轮又继续干活，那段的角色会从「正文」翻成「旁白」，样式跟着变一下 —— 这和 DSH 自己的判定是一致的。

### 已知的边界

- **命令说明 / 工具输出**依赖 `dsh-client-ui-tool` 的属性与类名（`data-caption`、`data-chat-call-id`、_codeBody _ioText 等）。属性是稳定的；类名是构建期哈希，插件用的是「包含 _codeBody」这类子串匹配，DSH 大版本升级后可能失配 —— 失配的表现是**那一项不生效**，不会翻错东西（样式表的其他规则照常）。
- 所有颜色都走主题 token（或对 token 做 `color-mix`），所以**浅色/深色切换后依然正确**，不需要为两套主题各配一遍。
- 模块只改样式，不改文字内容，也不会写入对话历史。

## 设置项

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| 启用自动翻译 | 开 | 关闭后不再发任何请求，已显示的译文一并移除 |
| DeepSeek API Key | 空 | 只保存在本机 `%DSH_HOME%/text-manager/settings.json`；平时接口只回传掩码，点「显示明文」时才经 loopback 路由取回一次 |
| 接口地址 | `https://api.deepseek.com` | OpenAI 兼容根地址，自动补 `/v1/chat/completions`；已经带 `/v1` 或完整端点也不会重复拼接 |
| 翻译模型 | `deepseek-chat` | 可以「获取模型列表」拉取接口的 `GET /models` 后从下拉里挑，也可以直接在输入框手填；列表会缓存进设置文档 |
| 翻译模型的思考模式 | 自动 | 自动=不发送该字段；开启/关闭会发送 `thinking: { type: 'enabled' \| 'disabled' }`。旧接口可能不接受，所以默认不发 |
| 只翻译英文思考 | 开 | 已基本是中文的内容直接跳过；超过 60 字符、又几乎没有成词英文的片段（纯路径 / 链接 / 标识符列表）也跳过。两者都省掉无意义的开销 |
| 翻译粒度 | 均衡 | 决定译文以多大的块出现，也就是请求数。实测本会话 385 块（82.6 万字符）：跟手 9,525 → **均衡 4,382（46%）** → 只按段落 3,700 左右 → 思考完再翻 ~1,000（11%）。越小越跟手、越贵。「思考完再翻」是**真的**等到这块内容说完才发请求（早期版本的单请求上限会抢在中间发货，1.6.0 修掉了） |
| 自动展开思考链 | 关 | 自动点开思考链本身，以及包住它的「工作进行」折叠行（Turn 耗时行 + 步骤分组表头），省得每次手点。同一处只展开一次：手动收起后保持收起；重新打开本选项会把当前已挂载的内容再展开一遍 |
| 同时翻译思考之间的零散文字 | 开 | 模型在工具调用之间输出的一两句说明（英文）也翻译。机制与思考块完全相同。关掉后只翻译思考块 |
| 连历史一起自动翻译 | 关 | 默认只自动翻译页面打开后新流式输出的内容。打开本项会连**已加载的历史内容**也自动翻译（会给以前所有对话花钱，慎用）。历史内容无论开关都可以用每行按钮手动翻 |
| 单次翻译上限（字符） | 1800 | 超过的段落会按词边界切开 |
| 请求超时（毫秒） | 45000 | 单次翻译请求的最长等待 |

两个自检按钮，都会先保存当前页面上的值再发起请求：

- **测试连接** —— 让 Host 发一次探针请求，把模型回复显示出来（验证 key / 地址 / 模型能通）。
- **测试翻译** —— 把下面文本框里的英文（预填了一段像真实思考的文字）**按翻译器真实的分段流程**切开、逐段调用翻译路由、再按同样的规则拼接，最后显示整段中文和分段数 / 耗时。这条链路和线上跑的是同一套代码。

页面顶部状态行会显示 `v1.6.3 · 运行中 · …`，第二行显示译文库条数与路径（`%DSH_HOME%/text-manager/translations.json`）。版本号来自 **Host 半边**：看不到版本号或版本号是旧的，说明 Host 半边还是旧构建，需要重启。

## 工作原理

### Host 半边（`lib/index.js`）

- 拥有设置文档 `%DSH_HOME%/text-manager/settings.json`（原子写）。
- 拥有**译文库** `%DSH_HOME%/text-manager/translations.json`：一段原文一条记录，key 是原文的 sha256，**刻意不含模型名** —— 译文就是「这段文字的中文」，所以重启、重开对话都回放同一段文字。上限 4000 条（LRU），写入按 1.5s 合并（流式翻译会连着写很多段）。
- 提供同源 JSON 路由族 `/text-manager/api/{settings.get, settings.update, settings.reveal, models.list, translate, test, test.translate}`，并做 **loopback 信任栅栏**（socket 地址、Host 头、`Sec-Fetch-Site`、Origin 与 `/api` 网关同一套判断），所以非本机浏览器拿不到这个接口。
- `translate` 的三个开关是「不回溯历史」和「译文固定」的实现核心：
  - 默认：先查译文库，命中直接回放，**不产生任何请求** —— 这就是重启后不重翻的原因；
  - `force: true`：跳过译文库、真的调模型、并覆盖旧译文（只有「刷新」按钮会这么传）；
  - `provider: false`：**只查不翻**，库里没有就回 `missing: true`（历史思考的首次扫描走这条，永远不花钱）。
- 翻译请求走 `POST {baseUrl}/v1/chat/completions`，带固定 system prompt（保留 Markdown 结构、代码块、路径、标识符与数字）；模型列表走 `GET {baseUrl}/v1/models`，并兼容 `{data:[{id}]}` / 裸数组 / `{models:[{name}]}` / `{data:["id"]}` 四种信封。
- 并发闸门最多 3 路。

### Browser 半边（`lib/client.js`）

设置页注册进 `settings.section` 槽位（`ctx.slots.inject('settings.section', …)`），导航里就多一项「文本翻译」。

翻译器本身走一条**没有官方槽位可用的路**：

- DSH 把内容渲染在 chat 包里，折叠交互由它独占 —— 没有任何槽位能替换一段内容的文本；而 `conversation.chat.node[assistant-step]` 是「覆盖已发布 UI」的键位，接管它等于重写聊天渲染。所以翻译器**附着在已提交的 DOM 上**：`MutationObserver` 找到行 → 从该行的 **React fiber props** 里读出源文本 → 按**段落**增量切分 → 在行**后面插入一个 React 不拥有的节点**渲染中文（React 重渲染不会把它冲掉，行消失时它跟着消失）。

翻译器认识**两类行**（`ROW_KINDS`），两者共用全部机制：

| 类 | DOM 钩子 | React props | 流式信号 |
| --- | --- | --- | --- |
| `reasoning` 思考块 | `[data-variant="think"]` | `ReasoningRow`：`text` + `running`/`usePresentation` | 行自己的 `data-state="running"` |
| `prose` 思考之间的零散文字 | `[data-chat-flow-kind="assistant-step"][data-chat-group-part="response"] div[class*="markdown"]:not([data-markdown-variant])` | `MarkdownText`：`text` + `streaming` | 外层 `AssistantMarkdown` 的 `data-streaming` |

`prose` 那一行没有官方的机器可读标记，所以它的选择器是「先粗筛、再验证」：类名只是预筛（CSS Modules 的运行时类名形如 `_markdown_1ypvv_5`，含 `markdown` 但不是固定值），**真正认定身份的是 fiber props**（`requireProps`）——元素只有在 props 属于 `MarkdownText` 时才被采纳。这样即使类名换了代、或者误匹配到同名的「markdown 文件图标」（那条路径上确实存在 `_markdown_1wejo_28`），也只会**少翻**而不会翻错东西。

工具卡片、命令行、compaction、system prompt 这些行都刻意不碰。

一切都能安静降级：读不到 props 就退回读可见 DOM 文本；没有 API Key 或开关关闭就完全不挂载翻译块；某一段内容的所有段落都被判定为「已是中文」时整块隐藏。

#### 「新的」是怎么判定的

一行内容只有在**被看到正在流式输出**时才算「新」，也只有这种行会自动花钱翻译。页面打开时就已经是完成态的行 —— 加载出来的历史、以前的对话 —— 一律不是「新」，只做**只查不翻**的扫描：库里有的原样显示，库里没有的留着按钮等你点。另外留了 2.5 秒宽限窗口：如果同一轮里另一行刚在流式输出，那么紧跟着出现的行（一两句话在一帧内就说完了）也算这一轮的新内容。

判定入口是 `refresh()`（打 `live` 标记）和 `allowsProvider()`（决定这次 pass 能不能花钱）；把「连历史一起自动翻译」打开后，`allowsProvider()` 对历史行也返回 true，就退回旧的全量行为。

#### 按钮与浏览器侧缓存

每行 companion 头部的按钮由 `actionOf(state)` 决定：还没翻全 → **翻译**（`force:false`，已存段落复用、只补缺的）；翻全了 → **刷新**（`force:true`，覆盖重译）。浏览器侧还有一层 `KNOWN` 段落表（含「确认没有」的 `null`），同一段文字在一页里只问一次；切换模型 / 接口 / 思考模式 / 「只翻译英文」时会清空这层（译文库仍以 Host 为准）。

`isNoop(state)` 决定整块是否隐藏：没有译文、没有待翻、且有过被跳过的段落 → 不占位置。

**自动展开**（默认关）只作用于思考块：思考内容被三层折叠挡住 —— 思考行自己的 disclosure、步骤分组表头（`button[data-process-activity]`）、以及 Turn 的「工作了 N 秒」折叠行（`button[data-turn-process]`）。开启后翻译器对**每一行已跟踪的思考**，去点开这三层里当前处于收起状态的控件。

关键是它**不会「只开一次」**。DSH 在一轮结束时自己会把整个思考过程折起来（分组表头被收起、成员的 disclosure 也被重置），再加上 Turn 那行折叠按钮。如果记账方式是「开过一次就不再管」，那打开开关后你看到的仍然是折好的思考 —— 这是 1.4.1 修掉的行为。现在只有**你自己的操作**才能让它停手：

- 在捕获阶段监听点击。**只有 `isTrusted === true` 的点击算你的意图**，插件自己 `dispatchEvent` 出来的点击 `isTrusted === false`，绝不算。
- 判断方向而不是一律记账：点击时那个控件**已经是展开**的，说明你要**收起**它 → 记下来，之后永不自动开；点击时它是**收起**的，说明你要展开 → 清掉记录。
- 所以：**你手动收起的那一层，插件不会再碰；DSH 自己折起来的，下一个扫描周期（≤1.5 秒）会自动重新展开。**

为了避免和 React 的异步提交打架（状态还没落到 DOM 上时再次点击会把它 toggle 回去），每个控件有 1.2 秒冷却。重新打开这个选项会清空冷却记录和你的收起记录，把当前挂载的内容再展开一遍。

点完还会把焦点还回去（聊天自身的 click 处理会 `focus()` 该控件，不还的话会把你正在输入的输入框抢走）。

## 成本（实测）

用本机会话日志重放插件自己的分段代码就能算出请求数，不必估算：

```powershell
node tools/measure-cost.mjs           # 这一版实际跑出来的请求数 / 段长分布 / 提示词开销
node tools/measure-granularity.mjs    # 各粒度档位的取舍曲线
```

某个真实会话（385 个内容块、82.6 万字符）的实测结果：

| 项目 | 数值 |
| --- | --- |
| 跟手档（一句一翻） | 9,525 次请求，中位段长 69 字符 |
| 均衡档（当前默认） | 4,382 次请求（46%），中位段长 159 字符 |
| 只按段落 | ~3,700 次请求（40%） |
| 思考完再翻（整块） | ~1,000 次请求（11%） |
| 切分依据 | 段落 2,828 次、**句末 6,697 次**、收尾 379 次 —— 句末切分才是成本主因 |

三个成本杠杆，从大到小：

1. **翻译粒度**（设置里可调）—— 句末门槛从 24 字符提到 320 字符，请求数直接减半；代价是中文晚一两句出现。
2. **提示词长度** —— 每条请求都要重发 system prompt。原来 495 字符（~124 token）占了全部 input token 的 **86%**；现在压到 146 字符（~37 token）。这一项让 input token 降到约四分之一。
3. **边界纪律** —— 「历史不自动翻」和译文库让重看、重启免费。要注意去重对**首次**翻译几乎没用：实测 9,465 个段里 9,433 个是唯一的（99%），因为每个句子片段都是新文本。译文库省的是重复阅读，不是第一遍。

另外两条与成本无关但同样重要的加固：

- **切分不落在代码围栏里** —— 切在半截 ``` 里会把两半都不配对地送给模型，模型会把代码翻坏（实测一次会话里有 300+ 处）。现在若切点落在一个未闭合围栏内，会退到该围栏起始的 ``` 之前；实在退不了（比如整块就是一个未闭合围栏）则整块一起发，保证不卡住。
- **429 / 5xx / 传输错误做指数退避重试**（最多 3 次，尊重 `Retry-After`）；4xx 立即失败，不浪费配额。以这个请求频率，撞限流是现实事件而不是极端情况。

### 一趟扫描只读一次 DOM 索引

这里的成本不是请求数，而是**主线程时间**，所以单独记一笔。

判断「这一段是正文还是旁白」要读 `[data-chat-group-part="response"]` 里同一轮的最后一条；自动展开要找到这一轮的 `button[data-turn-process]`。这两件事都只能靠全文档查询 —— 早先的写法是**每行查一次**，也就是一个扫描周期里 `行数 × DOM` 的工作量。

DSH 的转写区不虚拟化：点轮次轨道跳到很早的一轮时，内核会把**整段历史一次性 prepend**，几千行在同一帧挂载。这时「每行查一次」的扫描根本跑不完，而且 1.5 秒的定时器会在它跑完之前再次触发 —— 主线程被永久占满，表现就是**整个 DSH 窗口卡死**（实测 1065 条 assistant 消息的会话，一趟就是上千次全文档查询）。

现在的规则：

- **一趟扫描建一次索引**（`indexTranscript()`：两张 `Map`，一张 turn → 最后一行的 response，一张 turn → 仍未展开的 fold 按钮），`adopt` / `refresh` / `expand` 共用它。全文档查询从 `2 × 行数` 降到 2。
- **`expand` 点之前重新确认状态**：索引是这一趟开始时建的，同一趟里前面某行的点击可能已经把它展开，不能再点回去（这一条有单独的检查）。
- **每帧只花 8 ms**：`flushDirty()` 把「采纳新行」和「刷新脏行」都切片，超预算就交给下一帧（`FLUSH_BUDGET_MS` / `FLUSH_CHUNK`）。挂载几千行时界面照常能画、能滚。
- **1.5 秒的定时器不再把每一行都标脏**：真正的变化都由 MutationObserver 送来（正文、流式标记、折叠翻转），定时器只负责发现新行；每 10 个 tick 仍做一次全量刷新当兜底。所以一次漏掉的变更最多晚 15 秒，不会丢。

## 已知限制

- **思考块靠 DOM 附着。** 上游 chat 包若改变 `[data-variant="think"]` / `[data-disclosure-row]` / `[data-process-activity]` / `[data-turn-process]` 这些钩子或 `ReasoningRow` 的 props 形状，译文会静默停止出现、自动展开会失效（不会报错、不会破坏聊天）。译文是「贴在原文下面」的独立区块，而不是替换原文 —— 原文始终保留。
- **自动展开会把已加载历史里的思考也一并展开**（不只当前这一轮）。嫌长就关掉它。
- **内核转写区不虚拟化，插件修不掉它。** 点轮次轨道跳到很早的一轮时，内核会把整段历史一次性挂载，这一步本身就要几秒（行数越多越久，1065 条 assistant 消息的会话实测约 28 MB / 7828 条事件）。插件这边已把「每行全文档查询」的二次项去掉，所以不会再演变成整窗卡死；如果还嫌慢，就少用轨道做远距离跳转 —— 用「加载更早」一页页翻，DOM 是渐增的；或者给超长会话做 `/compact`、把新任务拆进新会话。
- **「新思考」的判定是「页面在看着它流式输出」**，所以：插件是在某轮推理进行到一半时才挂载的，这行仍会被认成新内容（它是 running）；而一轮推理如果在任何一次扫描之前就彻底结束、同一轮也没有别的行在跑，它会被当成历史，需要你点一下「翻译」。这是有意的取舍：宁可少花钱让用户点一下，也不要把旧对话全翻一遍。
- **段间没有共享上下文**：每段独立翻译，相邻段的术语/代词可能漂移（这一段叫「解析器」、下一段叫「词法分析器」）。这是流式分段的固有限制；想要一致就用「思考完再翻」档。
- **糟糕的切分会被冻结**：译文库按精确原文做 key，所以一次切在半句上的翻译会一直回放，除非你点那一块的「刷新」。
- **译文库是原文级共享的。** 同一段文字在不同对话里会命中同一条记录；改了分段上限（会把段落切成不同文字）或换了更长的原文就会产生新记录。库满 4000 条时按最久未用淘汰。
- **Host 半边改代码要重启**（见上）。
- **路由只服务 loopback**。本机 GUI 正常；通过 remote-web-ui 从其它设备访问时，翻译路由会被栅栏拒绝（浏览器半边会提示 Host 半边未重启或路由不可用）。
- API Key 以明文存在 `settings.json`（本机文件，和 DSH 其它本地设置同级）；「显示明文」按钮走的是同一条 loopback 栅栏。

  | --- | --- |
  | `--session=id1,id2` | 要搬的会话（默认：本工作区那三个） |
  | `--cwd=E:\path` | 目标工作区路径（默认：容器目录） |
  | `--drop-workspace=E:\path` | 会话搬走、目录也没了之后，删掉这个作废的工作区记录 |
  | `--workspace-only` | 只注册工作区、不碰任何会话日志（应用运行时也安全） |
  | `--dry-run` / `--force` | 只检查 / 跳过「应用已关闭」检测 |

### 为什么搬对话必须先退出应用

DSH **没有**「移动会话」这个操作。一个会话属于哪个工作区取决于它**自己头部记录的 `cwd`**（`dsh-workspace` 的成员资格是「只读头部」来验证的），而 `dsh-session-persistence-jsonl` 又**用同一个 `cwd` 推导日志路径**：

```text
<DSH_HOME>/sessions/<编码后的 cwd>/<会话 id>/session.v4.jsonl.zstd
```

所以「搬走」必须让三件事同时成立：改写头部帧里的 `cwd`、把会话目录挪到新的项目目录、在工作区记录之间移动会话 id。

而**应用运行中做这件事是危险的**：它在内存里持有旧的 header，每次追加事件都会**重新推导路径**（`resolveCurrentLog`），所以热搬会让新位置那份被冻住，事件继续写进旧路径 —— 历史被劈成两半。脚本因此在检测到 DeepSeek Harness 进程时直接拒绝运行。

### 脚本的安全设计

- 每个新文件**先写、后完整校验**（每一帧都能解压、每一行 JSON 都能解析、帧数与事件数与原文逐个相等），全部通过才删除原件。
- 头部帧的编码格式会先与产物里的写入器比对（`FHD` 必须一致，含 checksum 标志），再动手。
- `--dry-run` 走完全部检查但不写盘；重复执行幂等。
- 工作区只有**在它不拥有任何会话、且目录确实已不存在**时才会被删掉 —— 所以「目录暂时不可达」永远不会让人丢掉分组。

### 改名时改了什么

目录 `dsh-reasoning-translator` → `dsh-text-manager`，同时插件内部的身份标识一起改：包名、Loader 行 id、locale 命名空间、Host 路由前缀（`/text-manager/api`）、数据目录（`%DSH_HOME%/text-manager`）、DOM 属性前缀（`data-dsh-tm`）、界面名称（`文本翻译`），以及三处安装锚点：profile 的依赖项、`dsh.profile.bundles`、`pnpm-lock.yaml` 与 `node_modules` 链接。
